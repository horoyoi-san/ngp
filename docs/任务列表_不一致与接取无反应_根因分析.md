# 任务列表：内容不一致 / 重置不生效 / 接取无反应 —— 根因与修复

> 2026-09-23 · build 4229938 · 用户实测反馈后的第二轮
> 前提：上一轮的 `EventPanelInfo.EventsInfo` 修复已生效 —— **列表能显示了**。

---

## 0. 三个反馈，三个不同的原因

| 反馈 | 根因 | 性质 |
|---|---|---|
| 列表内容和任务容器不一致 | `TaskEventInfo.TaskId` 填的是**任务链里最旧**的一步 | 我上一轮引入的 bug，已修 |
| 重置任务容器后条目仍在 | `ResetQuestsAsync` **无条件**按 `startingTaskIds` 重新种 | 一直存在，已修 |
| 选择接取任务后游戏没反应 / 进不了任务流程 | **Spoon 图资源根本不存在**（不在任何随包资源里） | 外部资源缺失，本轮只做了取证 |

---

## 1. 列表内容 ≠ 容器内容

### 现象
服务端日志（`logs/console-20260923-034234.log`）：

```
1510: [03:45:51] [QUEST] SyncPlayerAllTask tasks=3 current=60004941 events=1
1511: [03:45:51] [QUEST][EVENT] event=1441 '天生救世主' task=60004938 status=21
                     ^^^^ 容器里 3 个任务、当前是 60004941，事件行却写 60004938
```

容器已经推进到 `60004941`（追逐火车），事件行的 `TaskId` 却一直钉在 `60004938`（隧道，大桥）。

### 原因

上一轮我写的选取逻辑是「**任务链里第一个"容器中确实有"的任务**」：

```csharp
// ❌ 旧逻辑：取到的是最旧的那一步
foreach (var t in TaskEventCatalogRepository.TasksOf(eventId))
    if (state.QuestStates.ContainsKey(t)) { taskId = t; break; }
```

容器是**累积**的（完成的步骤也留着），所以"第一个"永远是最早那一步。

事件 1441 的链 = `60004938 → 60004939 → 60004941 → 60004943 → …`，容器 = `{60004938, 60004939, 60004941}`
⇒ 旧逻辑取 `60004938`，正确值应是 `60004941`。

### 修复

新增 `CurrentTaskOfEvent(state, eventId)`：

1. 容器里的 `CurrentQuestTaskId` 若属于该事件 → 用它；
2. 否则从链尾往前找**最后一个**仍在容器里的步骤（= 玩家当前所在步骤）；
3. 都没有 → 回落 `StartTask`。

对应配置项 `gameplay.quests.eventTaskIdFollowsContainer`（默认 `true`）。

## 2. 重置后条目仍然显示

### 原因

```csharp
// ❌ 旧实现
lock (state.SyncRoot)
{
    state.QuestStates.Clear();
    state.CurrentQuestTaskId = 0;
    SeedConfiguredQuests(state);      // ← 立刻按 startingTaskIds 又种回来
}
```

`gameplay.quests.startingTaskIds = [60004938]`，所以"重置"完容器里又有了 `60004938`
⇒ 事件 1441 又被推导出来 ⇒ **面板条目当然还在**。

**这不是客户端缓存**，是服务端自己又灌了一遍。（上一轮已确认客户端只在收到
`SyncPlayerAllEventPanel` / `SyncEventPanelView` 时才动 `m_TaskEvents`，这两条我们都只发整包快照。）

### 修复

`ResetQuestsAsync(session, reseed = false)` —— **默认真清空**：

* 清 `QuestStates` / `QuestCounterValues` / `UnlockedQuestIds` / `CompletedSubQuestIds` / `StoryChain`；
* `CurrentQuestTaskId = 0`；
* 只有显式 `reseed: true` 才 `SeedConfiguredQuests`。

调试面板 API 也跟着改了：

```
POST /api/quest/reset   {"reseed": false}   ← 默认，真清空
POST /api/quest/reset   {"reseed": true}    ← 清空后按配置重新种
```

面板按钮：「重置任务容器」= 真清空；新增小按钮「重置并重新种」。

## 3. 接取任务后没有反应 —— Spoon 图资源不存在

### 3.1 客户端确实收到了并处理了

```
1625: [03:46:07] [QUEST] client AskAcceptAndSetCurrentTask task=60004938
1626: [03:46:07] [QUEST] SyncPlayerAllTask tasks=3 current=60004938 events=1
1632: [03:46:07] [QUEST] SyncCurrentTask type=0 task=60004938 firstTime=True
```

服务端接住了、回包了。客户端也没有任何 `deserialize failed`（整份 `Player.log` 里只有
`68745518 MoveWanderingData` 一个无关的）。

### 3.2 但客户端的任务图建不起来

```
log/Player.log:2777  GetRawFilePath failed, path:[GameRes/Spoon/HotRaid/Xinshouben.rcp] not found
log/Player.log:2793  LoadSpoon Xinshouben not found
                     ← SpoonRaidMgr.GetSpoonRaidGraphConfig("Xinshouben")
                       ← SpoonRaidMgr.LoadSpoonHelper ← TriggerManager.InitCurrentStage
log/Player.log:3130  Initialize SpoonTaskGraph Failed, taskId 60004938,eventId 0
                     taskLoaded:False hasGroup:False ctxNull:True taskGraphCount:0 groupGraphCount:0
```

客户端的任务系统是 **Spoon 驱动**的：任务能不能"跑"（目标节点 / GPS / 生成物 / 流程推进）
取决于 `SpoonTaskMgr.taskGraphs`。`taskGraphCount:0` ⇒ 一条任务图都没有 ⇒
`InitializeSpoonTaskGraph` 对**每一个**任务都失败 ⇒ 游戏里没有任何反应。

不只是 `60004938`，日志里这些任务全都在刷同一条失败：
`60004939 / 60004941 / 60004943 / 60000157 / 60000143 / 60000170 / 60000331 / 60000326 / 60000013`。

### 3.3 关键取证：这些资源**不在随包资源里**

客户端只会去三个地方找（`global-metadata.dat` 里的路径字面量）：
`GameRes/Spoon/HotRaid/`、`GameRes/Spoon/Task/`、`GameRes/Spoon/TaskRaid/`、`GameRes/Spoon/Event/`。

用 `L50Decrypt/tools/scan_head.py`（解 LZ4 头部后搜关键词）全库扫描：

| 目标 | 条目数 | `SpoonTask` | `SpoonRaid` | `HotRaid` | `Spoon/Task` | `Spoon/Event` |
|---|---|---|---|---|---|---|
| **CBT3 工作副本** `AnantaCBT3/.../Blocks` | 597,699 | 0 | 0 | 0 | 0 | 0 |
| **CBT3 原始副本** `AnantaCBT30000000/.../Blocks` | 597,699 | 0 | 0 | 0 | 0 | 0 |
| **CBT2** `AnantaCBT2/.../Blocks` | 227,235 | 1 | 0 | 0 | 0 | 0 |

对照组（证明扫描方法有效）：

* `Xinshouben` → 命中 `vfc_904#3867`（size 10,979），与上一轮独立扫描一致 ✅
* `Spoon` → 命中 **401** 条，但逐条看下来全是**组件名**，不是图数据：
  `vfc_92#68: Chongxiao_Quest04_Chasing | TaskSpoon`、
  `vfc_1586#2645: Gadgets_Common_WalkNearWall | SpoonSlotComponent | TimelineItem`、
  `vfc_904#2295: 23301187_23301187_Spoon | WildRoom`
  —— 是**挂在 prefab / Timeline 上的 Spoon 槽位组件**。
* CBT2 那唯一 1 条 `vfc_489#8`（202,453 B）同样是 prefab，内含
  `SpoonSlotAreaTrigger` / `SpoonTaskWorkAction` / `FinishWorkActionRef`（`L18.Spoon` 命名空间）。

**⇒ `GameRes/Spoon/HotRaid/*.rcp` 与 Spoon 任务图（`.tcp`）是热更新资源（patch CDN），
两个 CBT 的随包资源里都没有。**

佐证：两处安装的 `Ananta_Data/Patch/Blocks/` 都只有一个 **17 字节**的 `download_header.ehd`
（热更层是空的）。代理配置里的 `updateHost = l50.update.netease.com` —— 官方客户端是**从补丁 CDN 下载**这些图的。

### 3.4 结论

**这不是服务端能"修"出来的东西。** 官方客户端能跑任务流程，是因为它下载过热更补丁；
本机没有补丁层，所以 Spoon 图必然缺失，任务流程必然跑不起来。

## 4. 顺手修掉的两个语义 bug

### 4.1 `TaskState` 只有 4 个值，`SubmitQuestAsync` 写错了

```csharp
// dump.cs TypeDefIndex 32201  UX.Game.TaskState
NotAccept = 0 / Accepted = 1 / Submited = 3 / Aborted = 4
```

* 旧 `SubmitQuestAsync` 写 **1**（注释还写着"1 是已提交/可交付"）→ 客户端以为任务**还在进行中**
  ⇒ 交付后游戏里毫无变化。已改为 `Submited = 3`。
* 新增 `TaskState4229938` 常量类，`AcceptQuestAsync` / `AcceptStoryTaskAsync` 只接受这 4 个值。

### 4.2 `DisplayTaskStates` 名字与语义都是错的

```csharp
internal static readonly byte[] DisplayTaskStates = [1, 4, 5, 6, 8, 9, 17, 19];   // ❌
```

`TaskConfig.static.json` 里这**不是任务状态，是 `TaskConfig.Title`（任务分类 / tab）的集合**：

```
TaskTab1 = [1]        主线任务
TaskTab2 = [5, 6]     角色任务
TaskTab3 = [17, 9]    委托任务
TaskTab4 = [4,8,19,7] 支线任务
TaskTab5 = [4,8,19,2] 重玩任务
DisplayTask = [1,4,5,6,8,9,17,19]   ← 上面几个 tab 的并集
```

已改名 `DisplayTaskTitles` 并改作文档化用途：**解锁这些 tab**
（`SyncTaskTitleGuideUnlock`），顺便把静态表里的全部可显示 tab 都解锁一遍。
`AcceptQuestAsync` 里用 `DisplayTaskStates` 去"夹" `StartingTaskState` 的逻辑删掉了。

## 7. Spoon 图的三条出路（需要你选）

1. **拿到热更补丁**（正解，但依赖 CDN 还活着）。
   `Ananta_Data/Patch/Blocks/` 补上 `GameRes/Spoon/**` 的 vfc 块即可，服务端不用改。
   如果你手上有装过补丁的客户端目录（或补丁包），把 `Patch/Blocks` 拷过来就行。
2. **客户端侧兜底（BepInEx 探针）**：hook `SpoonRaidMgr.GetSpoonRaidGraphConfig`，
   拿不到就返回一个空的 `SpoonRaidGraphData`，让 `InitializeSpoonTaskGraph` 不再失败。
   预期收益：面板/目标文本可能由服务端计数 + 客户端 `TaskConfig.EventObjective` 渲染出来；
   **但游戏内流程（节点、生成物、GPS）依然是空的** —— 因为图里本来就没节点。
   风险：上一轮已证明探针能把"被容忍的失败"变成致命崩溃，需要按
   `il2cpp-probe-pitfalls` 的规则（只挂有返回值的 postfix + `[GUARD]`）写。
3. **接受现状**：任务**列表**能显示（本轮已可用），但任务**流程**跑不起来。
   把 `gameplay.quests` 当成"任务面板展示"用，不做剧情推进。
