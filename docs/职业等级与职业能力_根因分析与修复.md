## 1. 职业等级：`UrbanJobConfig.Level` ≠ 职业等级

这是本轮最容易踩错的一点。

| 表 | 字段 | 含义 | 例（NCCA Officer 11300003） |
|---|---|---|---|
| `UrbanJobConfig` | `Level` | **转职门槛**（要多少级才能接这个档位） | 301→1、302→5、303→10 |
| `UrbanJobLevelConfig` | `Level` / `Exp` | **等级上限与每级经验** | Lv1..**16**，L16 的 Exp=0 |

客户端 `gSpiritJobManager`：

```lua
function M:GetLevelCfg(jobClass, level)   -- 按 (JobClassId, Level) 查 UrbanJobLevelConfig
function M:GetLevelData(jobCfg, spiritTId)
    local jobData = spirit.SpiritInfo.SpiritJobInfo.AvailableJobs[jobCfg.Id]
    return self:GetLevelCfg(jobCfg.JobClass, jobData.Level), jobData   -- ← 用 SpiritJob.Level 反查
end
```

⇒ `SpiritJob.Level` 写的是**等级表里的 Level**。旧实现写 `UrbanJobConfig.Level`，
表现就是"Lv10 就顶格"或查不到配置。

### 本 build 的等级上限（`UrbanJobLevelConfig` 共 107 行 / 17 个职业大类）

| 职业大类 | 上限 | 最高档 |
|---|---|---|
| 11300003 NCCA Officer | **16** | 303 NCCA Inspector |
| 11300005 Truck Driver | **24** | 503 Senior Driver |
| 11300015 Street Leader | **20** | 1303 District Commander |
| 11300019 Tea Farmer | 10 | 1901 Tea Farmer |
| 11300017 Martial Artist | 5 | 1701 Martial Artist |
| 11300004 Hacker / 11300011 Inventor / 其余 | 3 | 403 / 12 / … |
| 11300016 / 11300018 / 11300020（无 `UrbanJobLevelConfig`） | 退回 `UrbanJobConfig.Level` 最大值 | 1801 / 1802 / 2002 |

### 为什么要"只留最高档"

客户端 `M:GetAvailableJobByClass(jobClassId)` 是：

```lua
for i, v in pairs(spirit.SpiritInfo.SpiritJobInfo.AvailableJobs) do
    local cfg = LTConfig.UrbanJobConfig.GetConfig(v.Job)
    if cfg and cfg.JobClass == jobClassId then return v, cfg end
end
```

`pairs` 顺序不确定 ⇒ 同时下发 301 和 303 会**随机**拿到低档，职业图标 / 等级显示就会抖。
所以 `jobTopTier=true`（默认）时 `AvailableJobs` 里每个大类只留最高档。

`CurrentJob` 也一起指到最高档（`SpiritJobInfo.CurrentJob` / `SyncSpiritJobInfo.currentJob`）。

### 新配置项（`gameplay.spiritContent`）

| 键 | 默认 | 说明 |
|---|---|---|
| `maxJobLevel` | `true` | `SpiritJob.Level` 取该大类上限 |
| `jobMaxExp` | `0` | 满级时 `SpiritJob.Exp`。**别填大值** —— `CheckJobIsPromote` 判据是 `jobLevelCfg.Exp < exp`，填大了会一直显示"可晋升" |
| `jobTopTier` | `true` | `AvailableJobs` 只留最高档 |

## 2. 天赋点满

三条独立的天赋线，全部点满：

| 线 | 字段 | 位置 | 树 |
|---|---|---|---|
| 职业天赋 | `SpiritJob.TalentInfo`（`SpiritJobTalentInfo`） | `SpiritInfo.SpiritJobInfo.AvailableJobs[jobId].TalentInfo` | `TalentTreeConfig.JobClassId == 职业大类`（99900006 NCCA / 99900010 Hacker / 99900009 Truck / 99900005 Street Leader / 99900012 Inventor / 99900004 Chaos Summoner） |
| 角色天赋 | `SpiritInfo.TalentInfo`（`SpiritTalentInfo`） | 登录包 | `TalentTreeConfig.SpiritId` 含该角色（99900000 主角 / 99900021..26 各角色） |
| 玩法天赋 | `PlayerClientInfoMinor.GameplayTalentInfos`（`Dictionary<uint, SpiritTalentInfo>`） | 登录包 | `TalentTreeConfig.GameplayId != 0`（1 Loot Hunter / 2 不要抬头！/ 3 Racing / 4 Basketball / 5 倒观天） |

### 为什么不能只给 `IsOrigin`

`TalentTreeTalentConfig` 共 **425 行**，其中 `IsOrigin == true` 的**只有 6 行**，且都在
99900015/99900016（赛车 / 篮球）——那两棵树是"玩法树"。旧实现只点亮 `IsOrigin`
⇒ 职业树和角色树**一个节点都不亮**，看起来就是"天赋没实现"。

`UnlockWholeTree4229938` 的做法：

- 遍历该树的**全部**节点，`Layer = max(LayerNum, 1)`；
- `TalentTreeRecordDict[treeId] = { SpentTalentPoint = Σ CostPoint, ActivatedNodeCount = 节点数 }`。

### 点数

| 键 | 旧默认 | 新默认 |
|---|---|---|
| `jobTalentPoint` | 35（原版升级给满） | **999** |
| `spiritTalentPoint` | 0 | **999** |
| `spiritTalentLevel` | 1 | **35**（`TalentTreeLevelConfig` 满级） |

`SpiritJob.TalentInfo.TalentPoint` 取 `max(存档, 配置)` —— 否则老存档里的 35 会把点数按回去。

新增开关：`unlockAllJobTalents` / `unlockAllSpiritTalents` / `unlockAllGameplayTalents`（都默认 `true`）。

## 3. ☠️ 顺手修掉的一个老 bug：`UrbanAbilities` 不是能力 id 列表

`SpiritUrbanSkill.UrbanAbilities` 是 **`List<int>`，长度 6**，内容是**六维属性值**
（力量 / 敏捷 / 耐力 / 智力 / 技巧 / 直觉），对应 `UrbanAttributeConfig` 的 6 行。

客户端 `SpiritManager:GetUrbanAttr(tid)`：

```lua
local urbanSkill = spirit.SpiritInfo.SpiritUrbanSkill
if urbanSkill and #urbanSkill.UrbanAbilities == 6 then return urbanSkill.UrbanAbilities end
local cfg = FightSpiritConfig.GetConfig(tid)
return cfg.UrbanAttribute        -- 例 [85, 82, 92, 72, 80, 68]
```

旧实现往这里塞 `FightSpiritConfig.DefaultUrbanAbility` 的 **id**（例莱卡娅 `[1, 100]`）：

- 长度 ≠ 6 ⇒ 客户端直接退回配置值，等于白写；
- 万一某角色正好有 6 条默认能力，六维面板会显示成垃圾数字。

现在 `maxUrbanAttribute=true`（默认）时写 **6 个 `UrbanAttributeConfig.MaxValue`（本 build 全 100）**；
关掉则写 `FightSpiritConfig.UrbanAttribute`（原版初始值）。

## 6. ⚠️ 为什么塔菲的订单列表只能是空的

### 能确定的部分

`ClientTruckOrderView`（reader 586）的 9 个字段顺序**已双重确认**：

1. `DefaultReturnCatalog4229938` 里 `AskGetTruckJobOrders`(63386469) /
   `AskRefreshTruckOrder`(63071191) 的形状串（由**本 build** 的 `RPCDeserializeAuto.lua` 生成）：
   `complex(586: list7-empty + ReadInt32 + ReadSingle + ReadUInt32 + ReadBoolean + dict7-empty + ReadBoolean + ReadUInt32 + ReadInt32)`
2. 中性包长度 27 字节，与手算逐字节一致。

⇒ `Orders / RewardPointSum / CustomerSatisfactionAverage / CurrentOrderId /
TruckGuideClicked / EventIdToAgent / AutoAccept / DefaultVehicleId / TotalIncome`

所以私服可以安全地回一个**结构正确的空视图**（订单为空、满意度 100、引导状态跟着存档走）。

### 不能确定的部分（为什么不能伪造订单）

`TruckJobOrderWrap`（reader 286）的字段表拿不到：

- IL2CPP metadata 里它是 **空类**（`[UXSerialize(0)] public class TruckJobOrderWrap {}`，
  `ux_all.il2cpp.h` 的 `_Fields` 也是空的）；
- 形状串**被生成器截断**了（只到
  `complex(286: complex(1582: complex(641: ReadInt32+ReadUInt32+UXVector3+UXVector3+ReadUInt64+list32-empty+ReadUInt32) …`）；
- 但**从这段前缀能看出 CBT3 改过**：reader 641（`TruckPosInfo`）在 CBT2 里是 5 个字段
  （`WpId/ConfigId/Pos/Rot/GadgetUId`），CBT3 变成 **7 个**（多了 `list32-empty` + `ReadUInt32`）。
  ⇒ 直接抄 CBT2 的 `TruckJobOrderWrap`（7 字段）**字段数不够**。

写一个字段数不对的结构 → 客户端 `deserialize failed` → **整个货运面板拿不到数据**，
比"空列表"更糟。所以这里的选择是：

- `AskAcceptTruckJobOrder` / `AskPreSettleTruckOrder`（返回 `TruckJobOrderWrap`）
  → 回 `DefaultReturnCatalog4229938` 的**中性包**（字段数天然正确，内容全 0）；
- `AskGetTruckJobOrders` / `AskRefreshTruckOrder` → 回结构正确的空视图。

### 要真正恢复"接单"需要做什么

把**本 build 的 `RPCDeserializeAuto.lua` 从 VFS 里解出来**（它就在客户端包里，
`DefaultReturnCatalog4229938` 就是由它生成的）：

1. `L50Decrypt/tools/l50_index.py` 读 `Blocks/ipa_header.ehd` 建索引；
2. 按路径哈希找到 `LuaFiles/LX6/Service/LuaGen/AutoGen/RPCDeserializeAuto.lua`
   （哈希函数见 skill `il2cpp-hash-crack`）；
3. `l50_payload.py` 解出载荷（LZ4 分块，≤128 KiB/块）；
4. 从 `Auto.Reader[286]` 直接抄字段表，然后 `TruckJobOrderWrap` 就能写对。

## 7. 线格式取证：`DefaultReturnCatalog4229938` 是本轮的关键工具

`Ananta.Server/Ananta.Core/Protocol/Client4229938/DefaultReturnCatalog4229938.cs`
（2368 行）里每个 method id 都有：

```csharp
case 63386469u: body = [0xFF,0xFF,0x01,…]; shape = "complex(586:list7-empty+ReadInt32+…)"; return true;
```

- `body` = **该返回体的中性字节**（全 0 实例）—— 直接用就绝不会 `deserialize failed`；
- `shape` = 客户端 reader 的**字段读取序列**（含 reader 编号）。

它是本轮**最快的取证入口**：先看 shape 确认字段数与计数编码，再用
`tools/disasm.py --rva <TypeSerializer.ReadXxx 的 RVA>` 复核（`TypeSerializer` 在
`ux_rpc/ux_game_all.dump.cs:172813`）。

本轮用它确认了三件事：

| 结论 | 证据 |
|---|---|
| `JobBoardInfo` 两个字典是 **dict7** 不是 dict32 | shape + `ReadJobBoardInfo`(0x9F145B0) 反汇编里的 `Read7BitEncodedInt` |
| `JobBoardEntry.State` 是 **1 字节** | `ReadJobBoardEntry`(0x9F22F00)：`ReadUInt32 ×3 → movzx byte → ReadUInt32 ×2 → cmp byte` |
| `SpiritHackerJobInfo` 确实只有 3 个字段 | `ReadSpiritHackerJobInfo`(0x9F5AE70)：`ReadStringOrNull` → marker+`ReadInt32`+N×(key+marker+`ReadHackerPostInfo`) → `ReadUInt32` |

> 附带一条：`UXBinaryReader.Read7BitEncodedInt`（0x9AAA1D0）结尾是 **`dec eax`**
> ⇒ 写侧要 `varint(n+1)`。这解释了 `UxWriter.Int7` 的 `+1`，也说明 `UxString` 的
> `WriteVarInt(len+1)` 是对的。
