## 2. 为什么「标记可骇入」只能走 `SyncUnitHackableState`

两层判据（`IDMAP1` + `midToExportOption`）实测：

| 方法 | id | C# 实现（`IDMAP1`） | lua 实现 | 能不能发 |
|---|---|---|---|---|
| `SyncUnitHackableState` | 68941159 | ✅ 存在 | ❌ `CSharpOnly` / 无 reader | ✅ |
| `SyncVehicleHackableState` | 68037721 | ❌ **不存在** | ❌ | ☠️ **别发**（发了没人接） |

```bash
# 判据命令
cd Assembly-CSharp-FULLDUMP
grep -c "IDMAP1 LX6-Service-GameSceneToClientImpl-SyncUnitHackableState0" dump.cs   # 1
grep -c "IDMAP1 LX6-Service-GameSceneToClientImpl-SyncVehicleHackableState0" dump.cs # 0
```

而**派车包本身没有「可骇入」字段** —— `PoliceVehicleSpawnClientInfo`
（`RPCDeserializeAuto.lua` 的 `Auto.Reader[453]`）**只有 5 个字段**：

```lua
Auto.Reader[453] = function (reader, obj)
    obj.Id          = reader:ReadUInt64()
    obj.VehicleId   = reader:ReadUInt32()
    obj.Position    = Base.ReadStruct(reader, Auto.Reader.UXVector3)
    obj.Facing      = reader:ReadSingle()
    obj.EulerAngles = Base.ReadStruct(reader, Auto.Reader.UXVector3)
end
```

⇒ 只能在**单位创建之后**补发 `SyncUnitHackableState`。

## 3. 修复

### 3.1 新增统一的标记入口

`GameRouter.MarkHackableAsync(session, entityId, token)` —— 发
`SyncUnitHackableState{ unitId, isHackable = true }`，并记下
「最近被标可骇入的车辆 id」。

### 3.2 三个调用点

| 位置 | 时机 | 说明 |
|---|---|---|
| `SpawnPoliceVehiclesAsync` | `SyncSpawnPoliceVehicles` **之后** | ★ 本次问题的正主（警车） |
| `SpawnDirectAsync`（`GameRouter.Vehicles.cs`） | `SyncSpawnVehicle` **之后** | 玩家自己召唤的车 |
| `RemarkAllVehiclesHackableAsync` | 手动/补救 | 把已知全部车辆重标一遍 |

☠️ **必须在单位创建包之后发** —— 客户端要先有单位才认这个标记。
以前只在**进世界那一刻**对「当时已存在的召唤车」发过一次，
之后召唤/派出的车永远拿不到标记。

### 3.3 自动驾驶回包修对车

`AskVehicleStartHackerAutonomousDriving` 的返回值被客户端当
`AutoDrive.Token` 用：

```lua
-- 442_LX6_SGUI_StoreDefine_HackAutoDrivingHUDPanelStore.lua:94
gClientToGameSceneDelegate:AskVehicleStartHackerAutonomousDriving(pos).Callback = function (err, token)
    if err ~= LTConfig.MessageConfig.Ok then ... else
        self:SetAutoDriving(true, token)
        LX6.Drive.AI.VehicleMissionManager.Instance:RegisterTaskDeletedEvent(token)
    end
end
```

⇒ 必须回**玩家正在接管的那辆车**。以前回 `LastSummonedEntity()`，
对着警车骇入时会回一辆不相干的车（或 0）。现在优先回
`LastHackableVehicleId()`，取不到才回退到「最后召唤的车」。

### 3.4 新增补救接口

```bash
POST /api/jobability/push  {"action":"hackable-vehicles"}
```

把「召唤车 + 派出的警车」重新标一遍可骇入（车已生成但当时没标上时用）。

## 4. ☠️☠️ 附带发现并修复：构建脚本**静默失效**

排查过程中发现 `bash tools/build.sh` 报 `[OK] build succeeded`，
但**产物时间戳一直不动**、`dotnet build` 一行输出都没有。

**根因**：

```bash
$ which env
/c/Users/Administrator/.local/bin/env      # ← 不是 /usr/bin/env！

$ cat ~/.local/bin/env
#!/bin/sh
# add binaries to PATH if they aren't added yet
case ":${PATH}:" in
    *:"$HOME/.local/bin":*) ;;
    *) export PATH="$HOME/.local/bin:$PATH" ;;
esac
```

这是 **uv / venv 装的 PATH 垫片脚本**（本意是 `source ~/.local/bin/env` 用），
**直接执行它只改一下 PATH 就退出**，什么都不跑，而且**退出码 0**。

`build.sh` / `run.sh` 里那句 `env \ "ProgramFiles=…" … dotnet build` 因此
**什么都没执行**，脚本还照样打印成功 —— 产物停在旧版本，排查了很久。

**修复**：两个脚本改用 `/usr/bin/env`（带 fallback）：

```bash
ENV_BIN="/usr/bin/env"
[ -x "$ENV_BIN" ] || ENV_BIN="$(command -v env)"
run() { "$ENV_BIN" "ProgramFiles=C:\\Program Files" … "$@"; }
```

修好后：

```
[2/2] build ...
已成功生成。
    0 个警告
    0 个错误
[OK] build succeeded
```

> **教训**：任何"构建/启动脚本报成功但没效果"的情况，
> **第一件事是对产物时间戳**，第二件事是 `which env` / `which <命令>`
> 确认没有 `~/.local/bin` 里的垫片覆盖真命令。

## 6. 还没做 / 边界

1. **街上的 Aether 车流** —— 客户端本地生成，服务端**不知道它们的实体 id**
   ⇒ 无法标记。只能骇「服务端生成的」车（召唤车 / 派出的警车）。
2. **Aether 人群 NPC** —— 走 `ClientStaticNpcInitData.EnableHack`（第 9 轮已修，默认 true），
   和车辆这条通道是两套机制。
3. **`AskHackVehicle` 的 `actionType`** —— 私服目前只回成功，不做真实效果
   （截图②那个「加速」选项）。要做需要按 `VehicleHackActionType` 分派。
